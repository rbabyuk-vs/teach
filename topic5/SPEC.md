# «Сейф» — специфікація вебзастосунку

Створи сейф із повідомленням, задай комбінацію й дедлайн та поділись посиланням. Хто знає правильний код, може відкрити сейф один раз. Якщо час сплив, повідомлення більше не можна отримати.

## Сценарій користувача

1. Автор вводить назву, повідомлення, код із трьох різних цифр, дату й час згоряння. Може додати текстову підказку.
2. Після створення застосунок показує посилання `/safes/<id>`, яке можна скопіювати. Саме посилання не містить коду чи повідомлення.
3. Гравець відкриває посилання, бачить назву, підказку, таймер і диск 0–9. Він фіксує по одній цифрі, може скинути набір і подати спробу. Диск доступний мишею, дотиком і через кнопки для клавіатури.
4. Неправильна спроба до дедлайну повертає кількість точних збігів та збігів на інших позиціях. Наприклад, код `472` і спроба `427` дають один точний збіг і два збіги не на своїх місцях.
5. Правильна спроба до дедлайну відкриває сейф. Сервер видаляє запис і повертає повідомлення в цій самій відповіді. Екран показує текст; повторне відкриття або перезавантаження сторінки його не повертає.
6. Якщо дедлайн минув, навіть правильна спроба не відкриє сейф. Якщо запис ще існує, сервер видаляє його та повідомляє, що сейф згорів. Якщо запис уже видалено, сторінка показує «Сейф більше недоступний».

## Архітектура

**React → публічне HTTP API → Supabase Edge Function `safe-api` → Postgres.**

- Доступ до API відкритий: користувацьких акаунтів, входу й сесій немає. Будь-хто з посиланням може подати комбінацію. Сервер генерує випадковий UUID для кожного сейфа. Публічного списку сейфів немає.
- Postgres зберігає дані між викликами функції. Таблиця сейфів у приватній схемі, не відкритій через Data API. Функція підключається до неї через серверний рядок підключення з обмеженими правами. Параметри підключення зберігаються в секретах функції.
- Для `safe-api` вимкнути платформену перевірку JWT (`verify_jwt = false`). Браузер не отримує облікових даних бази, правильного коду або повідомлення до успішного відкриття. Комбінація з трьох цифр — механіка гри, тому для повідомлень використовувати вигаданий вміст.

| Поле | Тип і обмеження |
|---|---|
| `id` | UUID, первинний ключ, генерує сервер |
| `title` | Текст, від 1 до 80 символів після обрізання пробілів |
| `hint` | Необов’язковий текст, до 160 символів |
| `message` | Текст, від 1 до 500 символів; лише пробіли не допускаються |
| `code` | Рядок із трьох різних ASCII цифр; `047` валідний |
| `created_at`, `expires_at` | `timestamptz`; дедлайн на момент створення має бути в майбутньому |

## Контракт API

Базовий шлях: `/functions/v1/safe-api`. Тіла запитів і відповідей — JSON, окрім `OPTIONS`. Усі дати — ISO 8601 з часовим поясом; сервер повертає UTC. Відповіді мають `Cache-Control: no-store`. Для фронтенду налаштувати CORS та відповіді на preflight.

| Метод і шлях | Запит | Успішна відповідь |
|---|---|---|
| `POST /safes` | `{"title":"Сюрприз","message":"...","code":"047","hint":"...","expiresAt":"<ISO 8601 у майбутньому>"}` | `201`: `id`, `title`, `hint` за наявності, `expiresAt`. React формує посилання з отриманого ID. |
| `GET /safes/:id` | Без тіла | `200`: `id`, `title`, `hint` за наявності, `expiresAt`, `serverNow`, `status: "locked"`. |
| `POST /safes/:id/attempts` | `{"guess":"427"}` | `200`: `{"status":"locked","exact":1,"misplaced":2}` для неправильної спроби в прикладі вище, або `{"status":"opened","message":"..."}` для правильної. |

| HTTP | Коли | Тіло відповіді |
|---|---|---|
| `400` | Некоректний JSON, поля створення, ID не у форматі UUID або комбінація | `{"error":"INVALID_INPUT"}` |
| `404` | Невідомий шлях або запису вже немає | `{"error":"NOT_FOUND"}` |
| `405` | Метод не підтримується на відомому шляху | `{"error":"METHOD_NOT_ALLOWED"}`; додати заголовок `Allow`. |
| `410` | Запит до наявного простроченого сейфа. Запис видалено. | `{"error":"SAFE_BURNED"}` |
| `500` | Неочікувана помилка | `{"error":"INTERNAL_ERROR"}` |

Сервер сам визначає час, стан і результат. Поля на кшталт `now` або `status` від клієнта не впливають на рішення. Код і повідомлення не записуються в логи. Повідомлення показується як звичайний текст.

## Одноразове відкриття й видалення

- Для перевірки коду заблокувати рядок сейфа в транзакції (`SELECT … FOR UPDATE`). Після отримання блокування прочитати актуальний час бази. Спочатку перевірити дедлайн, потім комбінацію.
- Якщо код правильний і час не сплив, видалити рядок у цій транзакції, зафіксувати її, тоді повернути повідомлення. Дві одночасні правильні спроби не можуть обидві отримати текст. Якщо з’єднання обірветься після видалення, повторний запит не відновить повідомлення.
- При `now >= expiresAt` будь-який валідний запит читання чи спроби до цього сейфа видаляє прострочений запис і повертає `410`. Пізніші запити отримують `404`. Коли таймер у браузері доходить до нуля, React робить GET, щоб підтвердити стан.
- **Без Cron:** доступ припиняється точно за дедлайном за серверним часом. Фізичне видалення простроченого запису відбувається автоматично при першому зверненні до нього після дедлайну. Якщо запитів немає, запис залишається в базі. Щоб видаляти його без жодного запиту, знадобився б планувальник або сховище з автоматичним TTL.

## Критерії приймання

- [ ] Через форму і прямий POST можна створити окремі сейфи. Після перезапуску функції активні сейфи залишаються доступними.
- [ ] Посилання відкриває сейф в іншому браузері. GET і неправильна спроба не розкривають код чи повідомлення.
- [ ] Правильна комбінація до дедлайну повертає текст один раз і видаляє запис. Два паралельні запити отримують не більше однієї відповіді з текстом.
- [ ] Рівно в момент дедлайну і після нього правильний код не відкриває сейф. Перше звернення до простроченого запису повертає `410` і видаляє його. Переведення годинника браузера не допомагає.
- [ ] Невалідні дані повертають `400`. Інтерфейс показує закритий, відкритий, згорілий і недоступний стани та помилку мережі. Спроба відкриття не повторюється автоматично після мережевої помилки.
