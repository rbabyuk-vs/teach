Ти — досвідчений веброзробник, product designer і методист, який створює навчальні застосунки для студентів-початківців.

Ми маємо спроєктувати інтерактивну браузерну гру з робочою назвою **Web Quest: достав запит до сервера**.

## Навчальний контекст

Цільова аудиторія — студенти, які:

* уже знайомі з HTML і CSS;
* лише готуються почати системне вивчення JavaScript;
* використовують AI-агентів для створення програм;
* повинні розуміти створений продукт, а не просто отримати готовий код.

Головна тема заняття — як узагалі працює веб:

```text
URL → DNS → IP → порт → HTTP-запит → сервер
                                      ↓
                         HTTP-відповідь → HTML → DOM
                                                   ↓
                                             JavaScript
```

Після роботи з грою студент повинен розуміти:

* різницю між клієнтом і сервером;
* що таке URL, протокол, домен і шлях;
* для чого потрібні IP-адреса та порт;
* що робить DNS;
* різницю між HTTP і HTTPS;
* модель «запит — відповідь»;
* базове призначення `GET` і `POST`;
* значення статусів `200`, `404` і `500`;
* як браузер перетворює HTML на DOM;
* як JavaScript може змінювати DOM.

## Концепція гри

Гравець повинен провести вебзапит від введення URL до побудови сторінки.

Гра має складатися приблизно з таких рівнів:

1. Розібрати URL на протокол, домен і шлях.
2. Вибрати правильну IP-адресу, яку повертає DNS.
3. Вибрати правильний порт для HTTP або HTTPS.
4. Вибрати метод `GET` або `POST` відповідно до завдання.
5. Визначити правильний статус відповіді: `200`, `404` або `500`.
6. Отримати HTML і зрозуміти, як із нього утворюється DOM.
7. Виконати фінальну місію: змінити текст, додати та видалити DOM-елемент.

Неправильна відповідь повинна не просто забирати бал, а коротко пояснювати помилку. Наприклад:

```text
404 — це статус HTTP-відповіді, а не номер порту.
```

Гравець повинен бачити:

* поточний рівень;
* прогрес;
* кількість балів;
* результат своєї відповіді;
* коротке навчальне пояснення;
* сформований HTTP-запит;
* відповідь сервера;
* фінальну вебсторінку.

## Важливі обмеження

* Це навчальна симуляція, а не справжній браузер.
* Не потрібно виконувати реальні DNS-запити.
* Не потрібно створювати сервер або базу даних.
* Не потрібно використовувати `fetch()` чи зовнішні API.
* Усе повинно працювати локально у браузері.
* Не використовуй React, Vue, Angular або інші фреймворки.
* Не використовуй зовнішні JavaScript-бібліотеки.
* Проєкт повинен складатися з:

```text
index.html
style.css
script.js
```

* Інтерфейс має бути адаптивним і працювати на телефоні та комп’ютері.
* Код має бути достатньо простим, щоб викладач міг пояснити його студентам-початківцям.
* Не ускладнюй першу версію drag-and-drop, складними анімаціями, авторизацією або серверною частиною.
* Не перетворюй застосунок на звичайний тест із питаннями. Гравець повинен бачити, як на кожному кроці будується шлях вебзапиту.
* Технічні пояснення повинні бути спрощеними, але правильними.
* Весь інтерфейс і навчальні тексти повинні бути українською мовою.
* Назви програмних конструкцій, HTTP-методів і статусів залишай англійською.

## Робота у два етапи

### Етап 1 — специфікація

Спочатку не пиши код.

Проаналізуй концепцію і постав мені лише ті запитання, відповіді на які справді змінять продукт. Об’єднай їх в один короткий список. До кожного питання запропонуй рекомендований варіант.

Якщо частину рішень можна безпечно прийняти самостійно, запропонуй розумний варіант замість зайвого запитання.

Після моїх відповідей підготуй повну специфікацію у Markdown.

Специфікація повинна містити:

1. Назву та коротку концепцію гри.
2. Навчальну мету.
3. Цільову аудиторію.
4. Основний сценарій користувача.
5. Послідовність рівнів.
6. Завдання на кожному рівні.
7. Правильні та неправильні варіанти відповідей.
8. Пояснення після кожної відповіді.
9. Систему балів і прогресу.
10. Стани гри:

* початок;
* активний рівень;
* правильна відповідь;
* неправильна відповідь;
* завершення;
* повторна спроба.

11. Вигляд сформованого HTTP-запиту.
12. Вигляд HTTP-відповіді.
13. Фінальну DOM-місію.
14. Структуру даних для рівнів.
15. Перелік необхідних HTML-елементів.
16. Основні JavaScript-функції та відповідальність кожної функції.
17. Правила адаптивного дизайну.
18. Обробку неправильних або неочікуваних дій.
19. Критерії приймання.
20. Набір тестових сценаріїв.
21. Поділ реалізації на невеликі послідовні етапи.

Для кожного рівня опиши:

* що бачить гравець;
* яке завдання отримує;
* які дії може виконати;
* яка відповідь правильна;
* які типові неправильні відповіді можливі;
* яке пояснення показує гра;
* як змінюється візуальна схема вебзапиту;
* скільки балів отримує або втрачає гравець.

Специфікація має бути достатньо точною, щоб після її затвердження інший агент міг реалізувати застосунок без додаткових припущень.

Наприкінці специфікації окремо додай:

```text
Відкриті питання
Припущення
Що не входить у першу версію
```

Після створення специфікації зупинись і попроси мене її перевірити. Не переходь до реалізації без мого прямого підтвердження.

### Етап 2 — реалізація

Після мого підтвердження специфікації:

1. Запропонуй короткий план реалізації.
2. Створи `index.html`, `style.css` і `script.js`.
3. Реалізуй застосунок невеликими логічними частинами.
4. Після кожної важливої частини перевіряй, що попередня функціональність не зламалася.
5. Не змінюй узгоджену специфікацію без пояснення.
6. Якщо виявиш суперечність або відсутнє рішення, зупинись і постав конкретне запитання.
7. Після завершення перевір усі критерії приймання та тестові сценарії.
8. Поясни структуру проєкту і ключові частини JavaScript зрозумілою для викладача мовою.

Почни з етапу 1. Код поки не створюй.
