# Лабораторна робота: динамічний каталог і повний сценарій користувача

## Мета роботи

Навчитися:

- отримувати дані із зовнішнього API;
- пояснювати призначення Promise, `fetch()`, `async` та `await`;
- обробляти успішну відповідь і помилки;
- створювати елементи каталогу через DOM;
- реагувати на дії користувача;
- зберігати й відображати стан сторінки;
- перевіряти повний сценарій користувача від першої дії до результату.

Ця робота об’єднує дві теми:

1. **Динамічний каталог.**
2. **Повний сценарій користувача.**

---

## Завдання

Створіть інтерактивну сторінку каталогу на **HTML, CSS і Vanilla JavaScript**.

Дані для каталогу потрібно отримати з API. Користувач повинен мати змогу переглянути дані, знайти або відфільтрувати потрібний елемент, вибрати його та завершити логічну дію.

Приклади сценаріїв:

- каталог товарів → кошик → оформлення замовлення;
- меню страв → вибрані страви → оформлення заявки;
- каталог рецептів → вибране → створення власної добірки;
- каталог товарів → список бажань → форма запиту;
- інший погоджений сценарій.

Сторінка працює тільки у браузері. Створювати власний сервер не потрібно.

---

## Джерело даних

Для каталогу використайте один із готових endpoint API:

```text
https://dummyjson.com/products
```

або

```text
https://dummyjson.com/recipes
```

API повертає об’єкт, усередині якого є масив `products` або `recipes`.

Наприклад:

```js
const response = await fetch("https://dummyjson.com/products");
const data = await response.json();

console.log(data.products);
```

Не копіюйте всі поля з API на сторінку. Визначте, які дані справді потрібні користувачеві.

## Етап 1. Спроєктуйте сценарій

Перед написанням коду коротко опишіть свій задум.

### 1. Опишіть сторінку

```text
Назва проєкту:
Що містить каталог:
Хто користуватиметься сторінкою:
Яку дію повинен завершити користувач:
```

### 2. Опишіть flow користувача

Запишіть послідовність дій від відкриття сторінки до кінцевого результату.

```text
1. Користувач відкриває сторінку.
2. Сторінка ...
3. Користувач ...
4. Якщо ..., сторінка ...
5. Після завершення користувач бачить ...
```

Приклад загальної структури:

```text
завантаження → каталог → пошук → вибір → форма → перевірка → підтвердження
```

Конкретний сценарій придумайте самостійно.

Самостійно вирішіть, які дані потрібно запитати у користувача.

|---|---|---|---|

Для кожного обов’язкового поля потрібно вміти пояснити, чому без нього неможливо завершити сценарій.

## Етап 2. Створіть динамічний каталог

Каталог повинен:

1. Отримувати дані через `fetch()`.
2. Використовувати `async/await` або `.then()`.
3. Перевіряти `response.ok`.
4. Перетворювати відповідь через `response.json()`.
5. Створювати картки на основі отриманого масиву.
6. Показувати щонайменше чотири властивості кожного елемента, наприклад:
   - назву;
   - зображення;
   - ціну або складність;
   - категорію, рейтинг чи короткий опис.
7. Мати кнопку дії на кожній картці.
8. Мати пошук або фільтрацію.
9. Показувати повідомлення, якщо результатів немає.

Картки повинні створюватися за допомогою JavaScript після отримання даних.

Для текстових даних з API використовуйте `textContent`. Якщо застосовуєте `innerHTML`, студент повинен пояснити можливі ризики.

---

## Етап 3. Реалізуйте вибір користувача

Користувач повинен мати змогу додати елемент до:

- кошика;
- списку вибраного;
- заявки;
- власної добірки.

Обрані елементи зберігайте в окремому масиві стану.

```js
let selectedItems = [];
```

Після кожної зміни масиву інтерфейс повинен оновлюватися.

Мінімальні можливості:

1. Додати елемент.
2. Побачити вибрані елементи.
3. Видалити елемент.
4. Побачити кількість вибраних елементів.
5. Не допустити нелогічного стану, наприклад оформлення порожнього кошика.

Якщо сценарій передбачає кількість або ціну, потрібно також показувати загальну суму.

---

## Етап 4. Завершіть сценарій формою

Після вибору елементів користувач повинен завершити дію через HTML-форму.

Форма повинна:

1. Містити щонайменше три змістовні поля.
2. Мати `label` для кожного поля.
3. Використовувати відповідні `id`, `name` і типи полів.
4. Мати хоча б одне обов’язкове та одне необов’язкове поле.
5. Перевіряти щонайменше три правила.
6. Показувати помилки безпосередньо на сторінці.
7. Не використовувати `alert()` як основний спосіб повідомлення.
8. Обробляти подію `submit` і викликати `event.preventDefault()`.

Після успішної перевірки покажіть підсумок усієї дії:

- що обрав користувач;
- основні дані з форми;
- кількість або загальну суму, якщо вони є;
- зрозуміле повідомлення про успішне завершення.

Реально надсилати замовлення на сервер не потрібно.

---

## Обов’язкові стани та помилки

Сторінка повинна коректно обробляти такі ситуації:

### Завантаження

Поки виконується запит, покажіть повідомлення на зразок:

```text
Завантажуємо дані…
```

### Помилка API

Якщо дані отримати не вдалося:

- сторінка не повинна ламатися;
- користувач бачить зрозуміле повідомлення;
- бажано додати кнопку повторного завантаження.

### Порожній результат

Якщо пошук або фільтр нічого не знайшов, покажіть окреме повідомлення.

### Неправильна дія

Не дозволяйте завершити сценарій, якщо:

- нічого не вибрано;
- обов’язкові поля порожні;
- значення не відповідають правилам;
- вибраний елемент більше не існує у завантажених даних.

### Успіх

Після успішної дії потрібно:

- показати підсумок;
- очистити старі помилки;
- визначити, що відбувається зі списком вибраного та формою.

---

## Вимоги до HTML і доступності

1. Використайте семантичні елементи: `header`, `main`, `section`, `article`, `form`.
2. Усі поля форми повинні мати пов’язані `label`.
3. Зображення повинні мати змістовний атрибут `alt`.
4. Усі дії мають бути доступні через кнопки, а не через звичайні `div`.
5. Повідомлення не повинні передаватися лише кольором.
6. Кнопки й поля повинні мати видимий стан `:focus`.
7. Сторінкою має бути можливо користуватися з клавіатури.

---

## Вимоги до CSS

Сторінка повинна:

- мати зрозумілу візуальну структуру;
- відображати картки за допомогою Flexbox або CSS Grid;
- бути адаптивною для телефона;
- мати однакові відступи й читабельний текст;
- візуально розрізняти звичайний стан, завантаження, помилку та успіх;
- не використовувати Bootstrap чи інші CSS-бібліотеки.

Дизайн студент створює самостійно. Оцінюється зручність, а не кількість декоративних ефектів.

Для складнішої версії реалізуйте одну або декілька можливостей:

- збереження вибраних елементів у `localStorage`;

- сортування за ціною, назвою або рейтингом;
- зміну кількості елементів у кошику;
- повторне завантаження після помилки;
- окреме вікно або секцію з детальною інформацією;
- індикатор загальної кількості вибраних елементів;
- блокування повторного додавання того самого елемента.

## Перевірка роботи

Студент повинен самостійно перевірити щонайменше такі сценарії:

| № | Сценарій | Очікуваний результат |
|---:|---|---|
| 1 | Сторінка відкривається | видно стан завантаження, потім каталог |
| 2 | API недоступне або URL неправильний | видно повідомлення про помилку |
| 3 | Пошук знаходить елементи | каталог показує відповідні результати |
| 4 | Пошук нічого не знаходить | видно повідомлення про порожній результат |
| 5 | Користувач додає елемент | вибраний список і лічильник оновлюються |
| 6 | Користувач видаляє елемент | елемент зникає зі списку |
| 7 | Спроба продовжити без вибору | дія блокується з поясненням |
| 8 | Форма містить неправильні дані | видно зрозумілі помилки |
| 9 | Усі дані правильні | видно повний підсумок і повідомлення про успіх |

Для перевірки помилки API можна тимчасово використати неправильну адресу endpoint.

## Захист роботи

Під час захисту студент повинен:

1. Пояснити задум і flow користувача.
2. Показати, звідки надходять дані та де у відповіді розташований масив.
3. Пояснити, що таке Promise та чому дані не доступні одразу.
4. Пояснити `async`, `await`, `fetch()`, `response.ok` і `response.json()`.
5. Показати код створення карток через DOM.
6. Показати, де зберігається стан вибраних елементів.
7. Продемонструвати успішний сценарій.
8. Продемонструвати помилку API, порожній результат і неправильне заповнення форми.
9. Пояснити правила валідації та вибір обов’язкових полів.
10. Виконати невелику зміну за завданням викладача.

Приклади змін під час захисту:

- показати в картці ще одну властивість;
- змінити правило пошуку;
- додати нове правило валідації;
- змінити текст одного стану;
- додати сортування;
- заборонити повторне додавання елемента;
- додати нове поле до підсумку.

Можна використовувати AI, документацію та приклади. Студент повинен розуміти зданий код, пояснювати власні рішення та вміти внести просту зміну.
